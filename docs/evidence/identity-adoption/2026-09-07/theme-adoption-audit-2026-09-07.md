# Project VE: read-only theme adoption audit

7 September 2026. Local source baseline: `292e65a8f7784df31591e94abe65fec47ddd23b6`, branch `codex/phase-6-practical-gate`. This assesses the current checkout, not a verified hosted deployment.

**Conclusion.** The frozen identity can be adopted through the existing presentation architecture. It requires a deliberate mapping of component roles and theme boundaries; changing a few root colours or importing the prototype CSS would not deliver a coherent result. The most important prerequisites are separating brand from status colours, mapping learner dark mode, consolidating signature placements, and defining how the existing tenant identity fields are presented. No further identity exploration is needed.

**Authority and scope.** The creative direction is frozen by the user's latest instruction: `project v/e`, Aperture A.2, Open signature, aubergine identity, Source Sans 3 with Source Serif 4, Aperture product grammar, and tenant-owned identity with a “Learning on project v/e” endorsement. Conceptual relationships remain brand rationale, not decoding instructions. The canonical name in ordinary text, metadata and accessible names remains Project VE. Technical export, role mapping and verification are adoption work; they do not reopen creative selection.

This audit made no changes to application code, theme values, existing identity studies, configuration, dependencies, database, GitHub issues or Wiki. This report is the only new deliverable. No build, database command, application mutation or deployment was run.

**What was inspected.** Source inventory across 457 tracked `.ts`, `.tsx` and `.css` files under `app/`, `components/` and `features/`, followed by targeted reads of theme definitions, shared primitives, brand placements, learner/organisation shells, content rendering, admin controls, auth/entry, PWA metadata and browser tests. The inventory found 116 files referring to `--ve-*`, 8 to `--learner-*`, 64 to `--admin-*`, 66 containing a hex or RGB colour literal, and 152 using `font-black`. These counts overlap and describe search scope, not defect counts or a list of files that all need editing. Shared styles occupy 4,973 lines in `app/globals.css`; welcome also has a CSS module.

**2. Confirmed adoption hazards**

**Colour roles are coupled.** The same green token controls primary buttons, success notices, good status badges, XP treatments and learning emphasis. [Learner Button](https://github.com/scothinks/project-ve/blob/292e65a8f7784df31591e94abe65fec47ddd23b6/components/ui/Button.tsx#L7) forces white text and a literal green shadow. [Admin button recipes](https://github.com/scothinks/project-ve/blob/292e65a8f7784df31591e94abe65fec47ddd23b6/components/admin/AdminPrimitives.tsx#L9) also couple primary, success and focus to `--ve-green`; [admin notices/statuses](https://github.com/scothinks/project-ve/blob/292e65a8f7784df31591e94abe65fec47ddd23b6/components/admin/AdminPrimitives.tsx#L90) repeat that dependency. Some newer admin controls instead consume `--admin-*`. Both generations need the same role contract.

A calculated substitution example shows the risk: retaining white text on the frozen dark primary `#d6bce2` produces **1.73:1** contrast; its frozen `#281b2e` foreground produces **9.45:1**. These are calculated future token pairs, not measured current-page failures. Likewise, the admin recipe's 14% colour-mixed focus ring would be approximately `#e8e2e4` over the frozen light surface, only **1.26:1**. Use an explicit visible focus treatment rather than assuming the old mixed ring remains suitable.

**Learner dark mode is a substantive gap.** Root tokens respond to `prefers-color-scheme`, but [learner shells](https://github.com/scothinks/project-ve/blob/292e65a8f7784df31591e94abe65fec47ddd23b6/app/globals.css#L451) impose light colours, literal gradients and `color-scheme: light`. Dashboard and other routes add further backgrounds. A dark root alone will not produce the frozen dark identity. Audit the alias cascade and gradient literals together. The current product uses OS preference; introducing a manual theme selector or persistence is unnecessary for identity adoption unless separately requested.

**Signature insertion has CSS traps.** Brand text appears directly in several components; no shared Aperture/brand-signature implementation was found in the inspected production roots. [Learner chrome](https://github.com/scothinks/project-ve/blob/292e65a8f7784df31591e94abe65fec47ddd23b6/components/navigation/LearnerTopChrome.tsx#L47) renders “Project Ve”; its [CSS](https://github.com/scothinks/project-ve/blob/292e65a8f7784df31591e94abe65fec47ddd23b6/app/globals.css#L2023) applies 800 weight and green. [Admin branding](https://github.com/scothinks/project-ve/blob/292e65a8f7784df31591e94abe65fec47ddd23b6/components/admin/AdminShell.tsx#L1166) uses uppercase/tracking styles and a separate VE tile. The organisation desktop selector [`.org-desktop-chrome__brand span`](https://github.com/scothinks/project-ve/blob/292e65a8f7784df31591e94abe65fec47ddd23b6/app/globals.css#L582) would style nested word/slash spans as small circular boxes if the new markup were inserted naively. The shared signature must own its internal typography and be insulated from these old selectors.

**Theme scope must include portals.** [Admin drawers](https://github.com/scothinks/project-ve/blob/292e65a8f7784df31591e94abe65fec47ddd23b6/components/admin/AdminDialog.tsx#L28), confirmation dialogs and selects render through Radix portals. A theme set only on an inner workspace wrapper may not reach portal content. Keep platform operational tokens available at the portal scope, and keep tenant identity tokens out of global root overrides. This is a scope check, not a reason to replace Radix or the established CMS foundation.

**Font adoption affects layout as well as appearance.** The app already uses `next/font/local`, so an existing local-loading path is available. Study font sources are full variable TTFs: Source Sans 3 is 646,340 bytes and Source Serif 4 is 1,209,508 bytes. Those source sizes are not measured shipped payloads. Prepare appropriately encoded/loaded assets, preserve licensing, check language coverage and italic content, and avoid loading the expressive family where unnecessary. Test line wrapping, table density, truncation, buttons, numeric alignment and fallback rendering. Do not import the full offline board or base64 font bundle into the app.

**4. Tenant ownership: supported data, incomplete presentation capability**

Tenant name, short name and logo already flow through authorised organisation context. Preserve [the protected route resolver](https://github.com/scothinks/project-ve/blob/292e65a8f7784df31591e94abe65fec47ddd23b6/app/o/[organizationSlug]/workspace.ts#L28) and its bounded workspace read. No new public organisation lookup is justified merely to show a logo on login. Public invitation pages must continue using their existing approved resolver fields; a slug or query parameter is not permission to expose organisation metadata.

The current model offers only `green`, `mission`, `store`, `violet` and `slate` [accent presets](https://github.com/scothinks/project-ve/blob/292e65a8f7784df31591e94abe65fec47ddd23b6/features/organizations/identity.ts#L1). These are stored enum values and validated by [the workspace mapper](https://github.com/scothinks/project-ve/blob/292e65a8f7784df31591e94abe65fec47ddd23b6/features/organizations/application/learner-workspace-context.ts#L141). Searches found transport/storage/editor references, but no direct consumption of the returned tenant accent by the inspected presentation components. Current tenant presentation largely uses platform/learner colours. Arbitrary tenant colours or tenant font selection are not an existing product capability to assume.

Adoption can immediately plan for tenant name/logo leadership and a neutral endorsement using existing authorised fields. Full configurable tenant colour/type support would be a separately specified capability, potentially involving validation, schema/API changes and safe fallbacks. Do not rename or reinterpret stored `green` as aubergine: tenant preset identity and platform brand identity are different roles.

There is also a breakpoint mismatch: [mobile organisation headers](https://github.com/scothinks/project-ve/blob/292e65a8f7784df31591e94abe65fec47ddd23b6/components/organizations/OrgLearnerMobile.tsx#L64) lead with the tenant; desktop chrome leads with Project Ve and shows the organisation as context. No “Learning on” endorsement implementation was found in the scanned production roots. Its placement needs an explicit responsive rule, not a text replacement. Keep it secondary, separate from Points, lifecycle/verification badges and workspace switching. The endorsement identifies infrastructure; it must not imply that the tenant adopts the platform's values framing.

Some tenant-logo slots use circular clipping or `object-cover`, including [admin identity](https://github.com/scothinks/project-ve/blob/292e65a8f7784df31591e94abe65fec47ddd23b6/components/admin/AdminShell.tsx#L809). Those rules can crop an organisation wordmark. Adoption should distinguish a logo slot from an avatar and preserve tenant artwork without wrapping it in A.2 or forcing the platform typeface onto the logo.

**5. Brand rationale and copy boundaries**

The current desktop login explicitly says “Project VE: Values Education” and “teaching and rewarding good values” ([source](https://github.com/scothinks/project-ve/blob/292e65a8f7784df31591e94abe65fec47ddd23b6/app/login/LoginPageClient.tsx#L42)); the [manifest description](https://github.com/scothinks/project-ve/blob/292e65a8f7784df31591e94abe65fec47ddd23b6/app/manifest.ts#L7) also narrows the offer to values education and rewards. These need a bounded brand-copy review when adoption is authorised. The frozen rationale should not become a required explanation in generic or tenant entry.

Do not perform a repository-wide replacement of Project VE with `project v/e`. The visual signature and endorsement use the frozen rendering; accessible names, ordinary references, metadata and technical identifiers remain canonical. Lesson categories, existing values content, assessment dimensions, legal copy and notification records are not logo labels.

The search also found values-education assumptions in authoring prompts, for example [the course generator](https://github.com/scothinks/project-ve/blob/292e65a8f7784df31591e94abe65fec47ddd23b6/lib/ai-learning-generator.ts#L401). Whether generic organisation training needs broader content-generation behaviour is a product question, outside a theme migration. Record that implication separately; it need not block visual adoption and does not authorise rewriting AI behaviour or existing learning content.

**6. Suggested adoption order, for future authorisation**

1. **Package the frozen system for production use.** One shared signature implementation with canonical accessible naming; A.2 optical/icon assets; properly loaded fonts; a role-based token contract and explicit status/tenant separation. Retire exploratory alternatives from the future production package without editing historical studies.
2. **Integrate foundational roles and both modes in a coherent batch.** Root, learner and admin mappings; paired button foregrounds; focus treatment; portal inheritance; shared controls. Selective adapters can bridge legacy variable names while consumers migrate. Avoid a new parallel styling framework or indiscriminate CSS-module extraction.
3. **Apply the grammar across the shared learning path.** Dashboard continuation, library, course/lesson and organisation delivery. Use existing read models and state. Confirm that “current” and “completed” remain distinct and that programme-specific progress is preserved.
4. **Complete identity placement across tenant, admin and public surfaces.** Tenant-led responsive chrome and neutral endorsement; mobile/collapsed admin marks; public/auth identity and bounded copy adjustments. Carry welcome-flow redesign as explicit #91 work rather than silently adding behaviour to a theme patch.
5. **Finish peripheral assets and verify the integrated product.** Install/push icons, browser colours, support host, transcript, empty/error/loading states and commercial disclosures. Confirm actual icon dimensions: the current manifest requests a 192px variant through a query parameter, while `app/icon.tsx` declares a fixed 512px output; correct export sizing must be verified during asset preparation.

These are dependency groups, not new approved implementation phases. No adoption work has been started by this audit. Arbitrary tenant theme configuration, new routing/auth behaviour, content-policy changes and hosted rollout require their own concrete scope.

**7. Acceptance evidence needed when adoption is implemented**

The existing gates are useful but do not establish frozen-theme readiness. [Admin workspace tests](https://github.com/scothinks/project-ve/blob/292e65a8f7784df31591e94abe65fec47ddd23b6/tests/e2e/admin-workspace-release.spec.ts#L178) cover operational structure and roles. [Lesson preview tests](https://github.com/scothinks/project-ve/blob/292e65a8f7784df31591e94abe65fec47ddd23b6/tests/e2e/lesson-preview.spec.ts#L124) check geometry at desktop/phone widths and explicitly require a 24px radius. Existing [Playwright configuration](https://github.com/scothinks/project-ve/blob/292e65a8f7784df31591e94abe65fec47ddd23b6/playwright.config.ts#L40) runs Chromium; no systematic dark-mode/contrast coverage appeared in the inspected browser tests. Preserve valid functional checks; revise visual contracts only where a deliberate adoption decision changes their requirement.

Future acceptance should demonstrate:

- Both modes across public/login, dashboard/library, reader/quiz, organisation learning, admin table/editor/drawer and tenant endorsement. Include long names, missing/wide tenant logos and mobile/collapsed navigation.
- The exact Open signature, an unchanged A.2 path, correct small icons, canonical accessible names and no old uppercase/descendant-span style leakage.
- Text/action/focus contrast on actual composited surfaces; keyboard focus and return; disabled/error/success states; zoom/reflow, small phones and long-content wrapping. The prototype's green checks do not substitute for product checks.
- Font fallback and loading stability, content/media readability, protected first-useful HTML, no added identity queries or cross-tenant cache, unchanged lesson/assessment/reward state.
- Appropriate typecheck/lint/build and focused browser/guardrail coverage once code changes. DB/RLS tests only if a separately approved change crosses those boundaries; do not run destructive resets just to inspect a visual theme.
- Preview comparison on a real phone, correct installed/browser/push assets and separate hosted rollout evidence before claiming release completion.

**Audit limits.** This is a source-backed adoption assessment, not a screenshot audit of the running product. No live/private tenant data, external support-widget internals, hosted state, email-provider templates, physical exports or real-device behaviour were inspected. Mathematical contrast examples are explicitly hypothetical substitutions. No test suite was run because application code was unchanged and the task was read-only. Tracked staged and unstaged diffs were empty at inspection; existing untracked identity/output work was preserved. The creative freeze is accepted without reopening identity studies.
